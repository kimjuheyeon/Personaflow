## MVP 구현 현황

이번 MVP에 포함된 범위:

- Flow UT와 빠른 화면 리뷰 모드 분리
- 테스트명, 시나리오, 미션, 진입 화면, 성공 화면 설정
- 업로드 순서 기반 기본 Flow 자동 생성
- 행동명/출발/도착 화면 수정과 수동 분기 추가
- 진입점에서 성공 지점까지 경로 사전 검증
- 페르소나별 독립 Flow 실행 및 행동 이벤트 저장
- 성공률, 첫 행동 정확도, 평균 단계, 경로 효율, 우회율, 회복률 계산
- Journey map, 주요 마찰, Tester session 중심 Flow UT 리포트
- 기존 요약, 발견 문제, 클릭 시뮬레이션, 인라인 채팅, A/B 기능 유지

후속 단계로 남긴 범위:

- Figma `flowStartingPoints` 및 `interactions` 자동 파싱
- 동일 페르소나 반복 실행과 표본 확장
- Live URL 브라우저 실행
- 개선 전/후 및 A/B Flow 비교
- 산업 벤치마크

## 1. 기획 결론

PersonaFlow의 기본 테스트 단위를 “화면”이 아니라 **하나의 사용자 미션**으로 바꾼다.

현재도 여러 프레임을 순서대로 배치하고 클릭 시뮬레이션 결과를 만들 수 있지만, 실제 분석은 사용자가 지정한 `Screen01 → Screen02 → Screen03` 순서를 AI가 따라가는 방식이다. 이 구조에서는 다음을 충분히 검증하기 어렵다.

- 사용자가 어디서 시작해야 하는지 알아차리는가
- 첫 행동을 올바르게 선택하는가
- 예상 경로가 아닌 다른 경로로 이동하는가
- 막힌 뒤 이전 화면으로 돌아와 회복하는가
- 어느 분기에서 반복적으로 이탈하는가
- 최종 과업을 실제로 완료했는가

따라서 새 Flow UT는 아래 세 가지를 제품의 중심 객체로 둔다.

1. **진입점(Entry point)**: 테스트가 시작되는 화면
2. **미션(Mission)**: 사용자에게 주어진 현실적인 과업
3. **성공 조건(Success criteria)**: 과업 완료를 판정할 수 있는 명시적 조건

프레임 피드백은 제거하지 않고, Flow UT에서 발견한 문제의 근거를 설명하는 하위 분석으로 유지한다.

## 2. Uxia에서 확인한 핵심 방식

Uxia의 공개 제품 설명과 사례를 기준으로 보면 UT 경험은 다음 구조다.

1. 타깃 사용자를 정의하거나 제품 정보를 바탕으로 synthetic tester를 만든다.
2. 프로토타입/제품, 테스트 미션, 시나리오, 테스터를 함께 설정한다.
3. 각 테스터가 같은 미션을 가지고 독립적으로 플로우를 탐색한다.
4. 테스트 중의 행동, 클릭, 기대, 생각을 단계별 transcript로 남긴다.
5. 결과를 반복 마찰, 과업 성과, 우선순위 인사이트와 벤치마크로 요약한다.

Uxia가 잘하는 부분은 “AI가 화면을 평가한다”가 아니라 **AI 테스터가 주어진 미션을 수행하고, 행동 로그에서 UX 문제를 합성한다**는 점이다.

공개 사례에서도 테스트 범위는 화면 수가 아니라 과업으로 설명된다.

- K-Chess: 소셜 가입, 사용자명 선택, 실력 설정을 포함하는 12프레임 온보딩 과업
- GVB: 처음 방문한 관광객이 Mastercard로 1시간 티켓을 구매하고 영수증을 요청하는 과업
- PMI/Cheil: 프로토타입 또는 URL, 미션, 시나리오, 대상을 정의하고 반복적으로 검증

### PersonaFlow에 가져올 것

- 테스트마다 하나의 명확한 미션과 시나리오를 먼저 정의
- 같은 미션을 여러 페르소나가 독립적으로 수행
- 결과를 화면별 의견보다 행동 경로와 과업 결과 중심으로 제공
- 요약 인사이트에서 개별 테스터의 step-by-step 근거까지 내려갈 수 있게 설계
- 같은 설정으로 재실행하여 개선 전후를 비교할 수 있게 설계

### 그대로 가져오지 않을 것

- 합성 사용자의 결과를 실제 사용자 조사와 동일하게 표현하지 않는다.
- 근거 없는 성공률이나 시간 값을 실제 측정값처럼 보여주지 않는다.
- SUS/SUPR-Q와 유사한 점수를 도입하더라도 설문 응답 또는 산식 없이 이름만 차용하지 않는다.
- Uxia의 화면 구성을 복제하지 않고 PersonaFlow의 강점인 Figma 프레임 연결, 페르소나 대화, 화면별 근거를 Flow UT 안에 통합한다.

## 3. 현재 PersonaFlow와 목표 구조의 차이

| 구분 | 현재 | 목표 |
|---|---|---|
| 테스트 단위 | 개별 프레임 또는 정렬된 프레임 묶음 | 하나의 사용자 미션 |
| 시작점 | 첫 번째 카드로 암묵 결정 | 사용자가 진입 화면을 명시 |
| 이동 방식 | 지정된 순서를 그대로 따라감 | 연결 그래프 안에서 테스터가 다음 행동을 선택 |
| 종료 방식 | 모든 화면 분석 후 종료 | 성공, 부분 성공, 실패, 중단으로 판정 |
| 분기/회복 | 표현 불가 | 우회, 뒤로 가기, 반복, 막힘 기록 |
| 결과 근거 | AI가 한 번에 생성한 walkthrough | 실제 시뮬레이션 이벤트 로그 |
| 핵심 지표 | 추정 완료율, 클릭 수, 오류율 | 성공률, 첫 행동 정확도, 경로 효율, 이탈/회복 |
| 문제 우선순위 | 심각도 중심 | 심각도 × 발생 빈도 × 과업 영향 |
| 화면 피드백 | 핵심 결과 | 플로우 문제를 설명하는 하위 근거 |

## 4. 제품 구조 제안

### 4.1 테스트 모드

새 테스트 생성 시 아래 모드를 제공한다.

1. **Flow UT — 기본/추천**
   - 진입점에서 미션을 수행하는 전체 여정 평가
   - 2개 이상의 연결 화면 권장

2. **빠른 화면 리뷰 — 기존 기능 유지**
   - 단일 화면 또는 연결 정보가 없는 이미지 평가
   - 정보 구조, 카피, 시각적 명료성에 적합

3. **A/B Flow 비교 — 후속 단계**
   - 동일 미션으로 A/B 플로우를 각각 실행
   - 화면별 우열이 아니라 성공률, 우회, 마찰 차이를 비교

### 4.2 지원 소스

| 소스 | Flow UT 수준 | 처리 방식 |
|---|---|---|
| Figma 프로토타입 | 권장 | 시작점과 프로토타입 interaction을 가져와 Flow graph 자동 생성 |
| 여러 이미지 | 제한적 지원 | 사용자가 화면 간 연결을 직접 설정 |
| 단순 이미지 순서 | Guided flow | 분기 없는 선형 경로로 테스트하고 한계를 명시 |
| Live URL | 2차 확장 | 실제 브라우저 에이전트가 클릭·입력하며 수행 |
| 사용 영상 | 3차 확장 | 사용 경로 이해/평가용이며 독립 탐색은 아님 |

Figma REST API는 파일의 `flowStartingPoints`와 노드의 `interactions` 정보를 제공하므로 자동 Flow graph 구성은 기술적으로 가능하다. 단, 복잡한 조건부 액션, 변수, 오버레이는 MVP에서 지원 범위를 명시해야 한다.

## 5. 새 테스트 생성 UX

### Step 1. 테스트 소스 연결

목표: 평가할 제품 경험을 불러온다.

- Figma 프로토타입 링크
- 이미지 업로드
- 가져온 화면 수, 감지된 플로우 수, 연결 누락 상태 표시
- Figma에 여러 시작점이 있으면 테스트할 Flow 선택

완료 조건:

- 분석 가능한 이미지가 존재
- Flow UT라면 화면이 최소 2개 이상

### Step 2. 미션 설계

목표: “무엇을 검증하는 테스트인지”를 고정한다.

필수 입력:

- 테스트명
- 사용자 시나리오
- 수행 미션
- 진입 화면
- 성공 화면 또는 성공 조건

선택 입력:

- 사전 조건
- 테스트에서 알려주면 안 되는 정보
- 기대 경로
- 최대 허용 단계
- 테스트 가설

#### 입력 예시

- 시나리오: “처음 암스테르담을 방문했고 대중교통 앱을 처음 사용한다.”
- 미션: “Mastercard로 1시간 이용권을 구매하고 이메일 영수증을 받아보세요.”
- 진입점: 홈
- 성공 조건: 결제 완료 화면 도달 + 영수증 요청 선택

#### 미션 작성 가이드

좋은 미션:

- 현실적인 상황과 목표가 있다.
- 버튼명이나 정답 경로를 노출하지 않는다.
- 완료 여부를 판정할 수 있다.

나쁜 미션:

- “우측 상단 가입 버튼을 눌러 Google로 가입하세요.”
- “이 화면이 이해하기 쉬운지 평가하세요.”
- 성공 조건 없이 “자유롭게 둘러보세요.”

### Step 3. Flow map 확인

목표: AI 테스터가 실제로 선택할 수 있는 경로를 검증한다.

화면 구성:

- 중앙: 노드/엣지 형태의 Flow map
- 좌측: 화면 목록과 연결 상태
- 우측: 선택한 화면의 상세 정보
- 상단: `진입점`, `성공 지점`, `도달 불가`, `연결 누락` 필터

노드 상태:

- 시작
- 중간
- 성공
- 대체 성공
- 오류/실패
- 도달 불가

엣지 정보:

- 트리거: 클릭, 제출, 뒤로 가기, 자동 전환
- 행동 대상: 버튼/링크/영역 이름
- 도착 화면
- Figma에서 자동 수집했는지, 사용자가 수동 설정했는지

이미지만 올린 경우:

- 화면 간 연결선을 직접 생성
- 연결선에 “다음”, “가입”, “결제”처럼 행동 이름 입력
- MVP에서는 정확한 hotspot 좌표보다 행동 이름과 목적 화면을 우선

Preflight 검증:

- 진입점에서 성공 지점까지 경로가 존재하는가
- 연결되지 않은 화면이 있는가
- 무한 순환 가능성이 있는가
- 성공 조건이 실제 노드/행동과 연결되었는가
- 기대 경로가 존재하는가

### Step 4. 테스터 구성

현재 Persona 설정을 유지하되 “페르소나 프로필”과 “테스트 당시 상태”를 분리한다.

페르소나 프로필:

- 역할, 디지털 친숙도, 기기
- 배경 경험
- 행동 성향
- 접근성 특성

테스트 상태:

- 이번 미션을 수행하려는 이유
- 알고 있는 정보
- 모르는 정보
- 긴급도/주의 수준

권장 기본:

- 3개 페르소나
- 페르소나당 3회 실행
- 총 9개 run

동일 페르소나를 여러 번 실행해 단 한 번의 LLM 응답을 “사용자 대표 의견”으로 과대 해석하는 문제를 줄인다.

### Step 5. 실행 전 확인

한 화면에서 아래 항목을 요약한다.

- 테스트 미션
- 시작/성공 조건
- Flow map 상태
- 페르소나와 실행 횟수
- 예상 실행 비용
- 지원하지 않는 interaction

CTA: `Flow UT 시작`

## 6. AI 테스트 실행 방식

### 6.1 현재 방식의 한계

현재는 모든 화면 이미지와 순서를 한 번에 모델에 전달하고, 모델이 전체 walkthrough와 완료율을 생성한다. 이 방식은 “실제 선택의 연속”이 아니므로 잘못된 경로, 뒤로 가기, 반복 시도 같은 행동을 신뢰성 있게 관찰하기 어렵다.

### 6.2 목표 방식: Event-driven agent loop

각 run은 다음 루프를 반복한다.

1. 테스터에게 현재 화면, 미션, 누적 행동, 현재 상태를 제공한다.
2. 현재 화면에서 가능한 행동 후보를 제공한다.
3. 테스터가 다음 행동 하나와 그 이유/기대/감정을 선택한다.
4. Flow graph에 따라 다음 화면으로 전환한다.
5. 이벤트를 저장한다.
6. 성공 조건, 실패 조건, 최대 단계 수를 검사한다.
7. 종료 조건을 충족할 때까지 반복한다.

중요 원칙:

- 모델이 존재하지 않는 버튼이나 경로를 만들 수 없게 가능한 행동을 제한한다.
- 모델의 말이 아니라 저장된 이벤트에서 지표를 계산한다.
- 각 단계에서 `행동 → 기대 → 실제 결과 → 생각 → 감정`을 기록한다.
- 동일 페르소나의 반복 실행은 독립된 run으로 저장한다.

### 6.3 이벤트 구조

각 이벤트는 최소 다음을 가진다.

- run ID / persona ID
- 현재 frame ID
- 선택한 행동과 대상
- 기대한 결과
- 실제 도착 frame ID
- 생각 aloud
- 감정
- 마찰 유형
- 뒤로 가기/재시도 여부
- step 번호

### 6.4 종료 상태

- `success`: 모든 성공 조건 충족
- `partial`: 일부 조건만 충족
- `failed`: 실패 지점 도달 또는 회복 불가
- `abandoned`: 최대 단계 초과 또는 테스터가 중단
- `invalid`: Flow 데이터 오류로 실행 불가

## 7. 리포트 UX

리포트의 첫 화면은 화면 점수 대신 **“이 미션을 완수할 수 있었는가”**에 답해야 한다.

### 탭 1. Overview

상단 핵심 카드:

- 과업 성공률
- 부분 성공/실패/중단 비율
- 첫 행동 정확도
- 평균 단계 수
- 경로 효율
- 가장 큰 이탈 지점

요약 문장 예시:

> 9회 중 5회만 과업을 완료했습니다. 가장 큰 병목은 `요금제 선택 → 결제수단` 전환이며, 초급 사용자 3명 중 2명이 뒤로 가기를 시도했습니다.

### 탭 2. Journey

- 전체 Flow map 위에 실제 이동 경로 중첩
- 노드별 방문 수, 이탈 수, 재방문 수
- 엣지별 이동 빈도
- 성공 경로와 실패 경로 비교
- 페르소나 필터

표현:

- 굵은 선: 자주 이동한 경로
- 붉은 노드: 반복 마찰/이탈
- 점선: 기대 경로
- 회색 노드: 방문되지 않은 화면

### 탭 3. Frictions

문제 우선순위 산식:

`우선순위 = 심각도 × 발생 빈도 × 과업 영향`

각 문제 카드:

- 문제 제목
- 발생 위치
- 영향을 받은 run/페르소나 수
- 과업에 미친 영향
- 대표 행동 로그/think-aloud
- 관련 화면
- 개선 제안

### 탭 4. Testers

테스터별 세션 재생 형태:

- 시작 시나리오와 미션
- 화면 썸네일
- 행동
- 기대
- 실제 결과
- 생각 aloud
- 감정 변화
- 성공/실패 판정

기존 `클릭 시뮬레이션` 탭을 이 구조로 확장한다.

### 탭 5. Screens

기존 화면별 발견 문제와 페르소나 채팅을 유지한다.

- Flow에서 해당 화면이 어떤 역할을 했는지 표시
- 이 화면에서 발생한 첫 행동 오류, 이탈, 재시도 표시
- 화면에 대한 추가 질문 가능

### 탭 6. Compare

같은 테스트를 재실행했을 때 제공한다.

- 이전 버전 대비 성공률
- 병목 이동 여부
- 해결된 문제 / 새로 생긴 문제
- 페르소나별 개선/악화

초기 MVP에서는 상세 통계 검정보다 방향성 비교로 한정한다.

## 8. 지표 정의

| 지표 | 정의 | 산식/근거 |
|---|---|---|
| 과업 성공률 | 성공 조건을 모두 충족한 run 비율 | success run / valid run |
| 첫 행동 정확도 | 진입점에서 기대 경로의 첫 엣지를 선택한 비율 | expected first action / valid run |
| 경로 효율 | 최단/기대 경로 대비 실제 이동 단계 | optimal steps / actual steps |
| 우회율 | 기대 경로를 벗어난 run 비율 | diverged run / valid run |
| 회복률 | 마찰 후 성공으로 돌아온 비율 | recovered friction / recoverable friction |
| 재방문율 | 같은 화면을 다시 방문한 비율 | revisit event / visit event |
| 이탈 지점 | 실패/중단이 가장 많이 발생한 노드 | 이벤트 집계 |
| 마찰 빈도 | 동일 문제를 경험한 run 수 | affected run count |

시간은 실제 사람이 측정된 값이 아니므로 MVP에서는 핵심 KPI에서 제외한다. 표시할 경우 반드시 `AI 시뮬레이션 추정치`로 라벨링한다.

## 10. MVP 범위

### 반드시 포함

- Flow UT / 빠른 화면 리뷰 모드 분리
- 미션, 시나리오, 진입점, 성공 지점 입력
- Figma flow starting point 및 interaction graph 수집
- Flow map 확인과 기본 수동 수정
- 페르소나별 독립 agent loop
- 이벤트 기반 성공/실패 판정
- Overview, Journey, Frictions, Testers 리포트
- 기존 Screens/인라인 채팅 연결
- 테스트 설정 저장 및 동일 조건 재실행

### MVP에서 제외

- 실제 Live URL 자동 조작
- Figma 조건부 변수와 복잡한 오버레이 완전 재현
- 실제 사용자 패널 모집
- 영상 녹화 업로드 분석
- 통계적 유의성 주장
- 산업 벤치마크
- 팀 협업/권한

## 11. 단계별 개발 로드맵

### Phase 1. Flow definition

- 데이터 모델 확장
- 미션 설정 화면
- 진입/성공 노드 지정
- 수동 선형/분기 Flow map
- Preflight validation

완료 기준:

- 사용자가 하나의 미션과 판정 가능한 Flow를 저장할 수 있다.

### Phase 2. Figma interaction import

- flowStartingPoints 파싱
- interaction에서 navigation edge 추출
- 지원/미지원 interaction 표시
- 자동 graph와 수동 보정 결합

완료 기준:

- 일반적인 Figma 온보딩/가입 플로우가 자동 연결된다.

### Phase 3. Agent runner

- 단계별 행동 선택
- 이벤트 저장
- 종료 조건 판정
- 반복 run
- 오류/재시도 처리

완료 기준:

- walkthrough가 한 번에 생성된 글이 아니라 실제 이벤트의 연속으로 재생된다.

### Phase 4. Flow report

- 과업 결과 집계
- Journey map
- Friction clustering
- Tester session
- 화면별 근거 연결

완료 기준:

- 각 요약 인사이트에서 해당 run과 이벤트 근거까지 추적할 수 있다.

### Phase 5. Compare

- 동일 테스트 버전 관리
- 개선 전/후 비교
- A/B Flow 비교로 확장

## 12. 성공 기준

제품 성공 기준:

- 새 사용자가 5분 안에 Flow UT 설정을 완료할 수 있다.
- 모든 테스트에 진입점과 성공 조건이 존재한다.
- 모든 핵심 인사이트가 하나 이상의 이벤트 근거와 연결된다.
- 테스트 실패와 제품 UX 실패가 구분된다.
- 동일 설정 재실행 시 결과 비교가 가능하다.

품질 가드레일:

- AI 결과임을 명확히 표시
- 실제 사용자 조사의 대체가 아니라 사전 검증/반복 개선 도구로 포지셔닝
- 연결 정보가 없는 이미지 테스트를 “독립 탐색”이라고 표현하지 않음
- 표본 수가 적을 때 정밀한 백분율을 과신하게 만들지 않음
- 페르소나별 단일 응답을 집단 대표 의견으로 표현하지 않음

## 13. 검토가 필요한 제품 결정

개발 전 아래 항목을 확정해야 한다.

1. 새 테스트의 기본 모드를 `Flow UT`로 바꿀지, 기존 화면 리뷰와 동등하게 노출할지
2. MVP에서 이미지 수동 연결을 포함할지, Figma 프로토타입에 우선 집중할지
3. 기본 실행 수를 `3 페르소나 × 3회`로 할지
4. 성공 조건을 화면 도달만 지원할지, 특정 행동까지 지원할지
5. 기존 `A/B 테스트`를 잠시 유지할지, Flow 비교가 완성될 때까지 보조 기능으로 둘지
6. 지표 이름에 “추정” 또는 “AI 시뮬레이션” 라벨을 어느 수준까지 표시할지

## 14. 제안 결정안

위 항목에 대한 1차 권고는 다음과 같다.

- 기본 모드: Flow UT
- 보조 모드: 빠른 화면 리뷰
- MVP 소스: Figma 프로토타입 우선 + 이미지 수동 선형 연결
- 기본 실행: 3 페르소나 × 3회
- 성공 조건: 성공 화면 도달 + 선택적 필수 행동
- 기존 A/B: 유지하되 “화면 A/B”로 명확히 라벨링
- 모든 수치: `AI 시뮬레이션 결과` 표시
